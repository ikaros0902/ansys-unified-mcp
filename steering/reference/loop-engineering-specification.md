# Loop Engineering 框架：方法論規格

## 排版慣例（全篇適用）

本規格以**工具無關的抽象語言**描述框架。為確保任何 AI coding agent 使用者皆能套用，全篇遵循以下排版慣例：

- **規格要求段落**：以抽象語言撰寫，描述「應該長什麼樣」，不綁定任何特定工具的專屬語法、指令或 SDK。這些段落構成規格的正式要求。
- **參考範例區塊**：任何特定工具的對應語法、指令或設定，一律以下列標註格式包裹，並與規格要求段落視覺分離。參考範例僅供理解，**不構成規格要求**。

> **參考範例（非規格要求）｜工具：<工具名稱>**
>
> 此區塊示範某特定工具如何對應上方的抽象要求。內容僅供參考，替換為其他工具時規格要求不變。

凡本規格出現工具專屬內容，皆置於上述區塊內；規格要求段落本身保持工具無關。

## 1. 文件總覽與結構

### 1.1 框架全貌（Introduction）

本規格定義一套與具體 AI coding agent 工具解耦的「Loop Engineering 框架」。其核心概念為：不再逐條手動提示 AI 代理，而是設計一個能自動「發現工作 → 分配任務 → 檢查結果 → 記錄狀態 → 決定下一步」的閉環系統（Loop），並讓此閉環能自動重複執行。

框架的交付物分為兩個層次：

1. **方法論規格層（本文件）**：以工具無關的抽象語言，定義 Loop 的六大組件、設計原則、反模式與成本風控標準。此層完全通用，不特化任何單一工具。
2. **可套用樣板集與可執行 kit（實作層）**：一組獨立的 Markdown 樣板檔案（見 `templates/`），以及一組可執行的落地元件（`loop.yaml`、Validator、Adapter_Mapping、Scaffolder），讓抽象概念可直接落地到專案中。

規格層描述「應該長什麼樣」，實作層提供「可直接跑起來的最小落地物」。兩層共用同一套術語與同一組閉環六階段，確保「無論坐在哪個工具裡都能工作的循環」。

### 1.2 六大組件

Loop 由下列六大組件構成。每個組件皆於本規格對應章節以工具無關的抽象語言定義：

1. **Automation_Trigger**（自動化觸發）— 見第 2 章
2. **Isolated_Workspace**（隔離工作空間）— 見第 3 章
3. **Skill_Document**（技能文件）— 見第 4 章
4. **Connector**（外部連接器）— 見第 5 章
5. **Sub_Agent_Role**（子代理角色）— 見第 6 章
6. **Memory_File**（持久記憶檔）— 見第 7 章

### 1.3 文件導覽

- 第 2–7 章：定義六大組件。
- 第 8 章：Verification_Condition 客觀化標準。
- 第 9 章：設計原則檢查清單（設計新 Loop 時逐項確認）。
- 第 10 章：反模式檢查清單（審查既有 Loop 時逐項比對）。
- 第 11 章：成本與風險控管標準。
- 第 12 章：Example_Loop 參考案例。
- 第 13 章：Template_Set 目錄（列出每個樣板的用途與建議存放位置）。

> _骨架備註：第 1.1–1.3 節於任務 1 建立；六大組件與各標準章節內容由任務 2–4 填入；第 13 章 Template_Set 目錄由任務 7 回填。_

## 2. Automation_Trigger（自動化觸發）

Automation_Trigger 是驅動一個 Loop 開始執行的機制。它回答「這個閉環在什麼時機被啟動」，是閉環六階段中的第一階段（於 `loop.yaml` 對應 `trigger` 欄位）。本章以工具無關的抽象語言定義觸發標準：任何具備排程或事件機制的工具，皆可依此標準設計 Loop 的自動化觸發，而無須改寫本章的規格要求。

### 2.1 兩種觸發類型

每個 Automation_Trigger 必須歸屬於下列兩種類型之一：

1. **定時觸發（Schedule-based）**：依時間排程週期性啟動 Loop，與外部狀態變化無關。適用於「不論是否有新變化，都希望定期執行一次」的循環，例如每日彙整、週期性健檢。定時觸發的觸發條件以「時間規則」表達（例如某頻率、某時刻、某週期）。
2. **事件觸發（Event-based）**：由外部系統發生的特定事件啟動 Loop，僅在事件實際發生時執行。適用於「有變化才需要反應」的循環，例如程式碼推送、問題單建立、CI 工作失敗。事件觸發的觸發條件以「事件描述」表達（哪個來源的哪類事件）。

兩種類型描述的是**啟動時機的來源**（時間 vs 外部事件），與使用哪種工具無關。使用者為 Loop 選定類型後，應以本章要求的三欄位記錄其觸發設定。

> 成本取捨提示：在無變化時定時觸發會產生空轉執行，事件觸發則僅在有變化時消耗資源。成本與頻率的權衡標準見第 11 章（成本與風險控管）。

### 2.2 記錄要求：觸發類型、觸發條件、執行頻率

當使用者為某個 Loop 定義 Automation_Trigger 時，**必須**記錄下列三個欄位，缺一不可：

| 欄位 | 說明 | 範例（抽象、非工具語法） |
| --- | --- | --- |
| 觸發類型 | 屬於定時觸發或事件觸發 | `定時觸發` / `事件觸發` |
| 觸發條件 | 觸發的具體條件描述：定時觸發填時間規則，事件觸發填事件來源與事件類型 | 「每個工作日早上」／「主線分支有新推送時」 |
| 執行頻率 | 預期的執行頻率，建議含頻率單位；用於成本評估與依產出品質調整 | 「每日一次」／「每次事件發生時，估計每日約 5–10 次」 |

記錄要求說明：

- **觸發類型**界定此觸發的來源類別，決定觸發條件如何填寫。
- **觸發條件**以抽象語言描述「什麼情況下啟動」，不寫成任何工具的排程語法或指令。
- **執行頻率**即使是事件觸發也須估計（例如以每日預期事件次數表達），因為執行頻率是成本與風險控管（第 11 章）的輸入；本章要求每個 Automation_Trigger 皆記錄執行頻率。

此三欄位對應 Template_Set 中的 `automation-trigger.template.md` 樣板，使用者可直接於樣板中填寫。

### 2.3 工具無關聲明

本規格**不規定**任何特定工具的排程語法、指令格式或設定檔結構作為 Automation_Trigger 的定義方式。觸發類型、觸發條件與執行頻率一律以抽象語言記錄；「某工具用哪個 hook、哪種 cron 寫法、哪個設定欄位」等屬於各工具的落地細節，不是本規格的要求。使用者只要在目標工具中找到對應的排程或事件機制，即可實現本章描述的抽象觸發標準。

下列參考範例示範某些工具如何對應上方的抽象要求，內容僅供理解，替換為其他工具時本章規格要求不變。

> **參考範例（非規格要求）｜工具：泛用 cron 排程器**
>
> 抽象要求「每個工作日早上定時觸發」在支援 cron 的排程機制中，可能寫成類似 `0 9 * * 1-5` 的五欄位運算式（分、時、日、月、星期）。此運算式是工具落地細節，非本規格對觸發條件的表達要求；規格層僅要求記錄「觸發類型＝定時觸發、觸發條件＝每個工作日早上、執行頻率＝每日一次」。

> **參考範例（非規格要求）｜工具：事件式 hook 機制**
>
> 抽象要求「主線分支有新推送時事件觸發」在支援事件 hook 的工具中，可能對應某個「on push to main」的事件監聽設定。該設定的具體語法屬工具落地細節；規格層僅要求記錄「觸發類型＝事件觸發、觸發條件＝主線分支有新推送、執行頻率＝每次推送時（估計每日約 N 次）」。

## 3. Isolated_Workspace（隔離工作空間）

Isolated_Workspace 是讓多個 Sub_Agent_Role 能並行工作而不互相覆蓋彼此變更的隔離工作空間機制。當一個 Loop 同時派出多個代理各自修改專案檔案時，若所有代理共用同一份工作副本，彼此的寫入會互相干擾、覆蓋，導致產出不可信。Isolated_Workspace 藉由「每個並行工作單元擁有各自獨立的檔案空間」解決此問題，並在工作完成、通過驗證後把變更合併回主線。本章以工具無關的抽象語言定義隔離工作空間標準：任何具備工作副本隔離與合併能力的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 3.1 概念定義與必備特性

Isolated_Workspace 是一個**與主線及其他工作空間彼此隔離的工作副本**，代理在其中讀寫檔案的行為不會即時影響主線或其他並行工作空間，直到經明確的合併步驟為止。

任何宣稱實現 Isolated_Workspace 的機制，**至少必須具備下列兩項必備特性**：

1. **檔案系統隔離（File-system isolation）**：每個工作空間擁有自己的一份檔案視圖，其中的新增、修改與刪除不會即時反映到主線或其他工作空間。並行的兩個工作空間對同一檔案的變更彼此不可見，直到合併發生；因此多個代理可同時作業而不互相覆蓋。
2. **可合併回主線（Mergeable back to mainline）**：工作空間中的變更必須能以可控、可追溯的方式合併回主線，且合併時能偵測與主線或其他已合併變更之間的衝突，交由後續處理，而非默默丟失任一方的變更。

上述兩項為**必要條件**：缺少檔案系統隔離則無法防止並行覆蓋；缺少可合併回主線則工作成果無法整合進正式產物。除必備特性外，實務上通常還期望具備可拋棄性（實驗失敗時可整份丟棄而不污染主線）與可追溯性（能回答某變更來自哪個工作空間、哪個角色），但本規格僅將前述兩項列為判定是否構成 Isolated_Workspace 的最低標準。

### 3.2 實現機制類型與等價關係

Isolated_Workspace 是一個抽象概念，可由多種具體機制實現。下列**至少三種機制類型**皆滿足 3.1 的兩項必備特性，因此彼此在本規格意義下**等價**：任選其一皆能作為 Loop 的 Isolated_Workspace，Loop 的其他部分無須因所選機制不同而改寫。

| 機制類型 | 檔案系統隔離的達成方式 | 可合併回主線的達成方式 |
| --- | --- | --- |
| **版本控制工作樹（version-control worktree）** | 同一版本庫掛出多個獨立工作目錄，各目錄有自己的檔案內容與作業狀態 | 以版本控制的合併/整併機制把某工作樹的提交併回主線，並在衝突時提示 |
| **獨立分支複本（isolated branch / clone）** | 每個工作單元在自己的分支或完整複本上作業，檔案變更僅存在於該分支/複本 | 以分支合併或複本回推的方式整合回主線分支，並偵測衝突 |
| **容器化沙箱（containerized sandbox）** | 每個代理在獨立容器/虛擬檔案系統中作業，容器內檔案變更與宿主及其他容器隔離 | 將沙箱內產出的變更（如 patch、diff 或檔案集）匯出後套用回主線，套用時檢查衝突 |

**等價關係說明**：三者的實作技術截然不同（版本控制原生功能、分支複製、作業系統層隔離），但**對 Loop 而言提供相同的抽象契約**——「隔離的檔案視圖 + 可控的合併回主線」。因此 Loop 的設計只依賴此抽象契約，不依賴任一機制的具體技術；更換機制不改變 Loop 對 Isolated_Workspace 的使用方式。此清單為非窮舉範例，任何同時滿足 3.1 兩項必備特性的其他機制，同樣可視為等價的 Isolated_Workspace 實現。

> **參考範例（非規格要求）｜工具：Git**
>
> 版本控制工作樹在 Git 中可能以 `git worktree` 對應，獨立分支複本可能以 `git branch` 搭配 `git clone` 對應，合併回主線可能以 `git merge`／`git rebase` 對應。這些指令是工具落地細節，非本規格對 Isolated_Workspace 的表達要求；規格層僅要求所選機制滿足「檔案系統隔離」與「可合併回主線」兩項必備特性。

### 3.3 多角色並行時的獨立工作空間規則

當一個 Loop 中有多個 Sub_Agent_Role **同時修改同一組檔案**時，本規格**要求該 Loop 為每個 Sub_Agent_Role 指派各自獨立的 Isolated_Workspace**，不得讓多個並行修改的角色共用同一個工作空間。此規則直接對應「防止並行覆蓋」的目的：

- 每個並行進行寫入的 Sub_Agent_Role 對應**恰好一個**專屬的 Isolated_Workspace，其變更先侷限在該工作空間內。
- 各工作空間彼此隔離（3.1 特性一），因此任兩個角色的變更在合併前互不可見、互不覆蓋。
- 只讀而不修改檔案的角色（例如唯讀的 Explorer、Reviewer，見第 6 章）不產生會互相覆蓋的寫入，可不強制各自獨立的寫入工作空間；本規則針對的是**並行修改同一組檔案**的角色。

Memory_File（第 7 章）中的進行中事項應記錄每個事項所屬的 Isolated_Workspace，以維持「哪個角色在哪個工作空間作業」的可追溯性。

### 3.4 合併回主線前的驗證步驟

Isolated_Workspace 中的變更在合併回主線**之前**，**必須**完成下列驗證步驟；未通過者不得併入主線：

1. **通過該 Loop 的 Verification_Condition**：合併前，該工作空間的產出必須滿足 Loop 所定義、可客觀驗證的完成條件（見第 8 章），例如指定測試全數通過、靜態檢查無錯誤或指標達門檻。
2. **由檢查者角色審查（製造/檢查分離）**：產出結果的變更須經與製造者不同的檢查者 Sub_Agent_Role 審查核准，避免自我審查的寬容偏差（見第 6、8 章）。
3. **衝突偵測與解決**：合併前須偵測該工作空間與主線（及其他已合併變更）之間是否存在檔案衝突；若有衝突，須先解決再合併，不得默默覆蓋任一方變更。

只有同時通過上述步驟的變更，才可合併回主線。這些步驟以抽象語言描述「合併前應完成什麼檢查」，不綁定任何工具的合併指令或審查介面；使用者只要在目標機制中落實「條件驗證、獨立審查、衝突處理」三者，即符合本章要求。

## 4. Skill_Document（技能文件）

Skill_Document 是以文件形式編碼專案知識與慣例的組件，供 AI 代理在 Loop 執行時**按需載入**。它回答「這個代理在做某類工作時，應該知道哪些專案特定的知識、慣例與陷阱」。若把所有專案知識一次塞進代理的上下文，會產生高昂且多半用不上的上下文成本；Skill_Document 以**漸進式披露（Progressive Disclosure）**原則解決此問題：平時只讓代理看到「這份技能是什麼、何時該用」的最小資訊，唯有在確認適用時才載入完整內容。本章以工具無關的抽象語言定義技能文件標準：任何能承載結構化文字並支援按需載入的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 4.1 四欄位標準結構

每一份 Skill_Document **必須**包含下列四個欄位，缺一不可：

| 欄位 | 說明 | 用途 |
| --- | --- | --- |
| **名稱（name）** | 此技能的簡短識別名，於專案內唯一 | 供索引清單與代理指涉此技能 |
| **描述（description）** | 一句話說明此技能涵蓋什麼、解決什麼問題 | 供代理在**不載入詳細內容**的情況下判斷是否可能相關 |
| **適用條件（applicability）** | 明確描述「什麼情況下這份技能才該被載入」的條件 | 作為漸進式披露的載入判準（見 4.2） |
| **詳細內容（body）** | 技能的完整內容：專案慣例、操作步驟、常見陷阱等 | 僅在適用條件成立時才載入，構成代理實際依循的知識 |

其中**名稱與描述**構成 Skill_Document 的「輕量識別層」，體積小、可長期常駐；**適用條件與詳細內容**構成「按需載入層」。這四欄位的切分是漸進式披露得以運作的前提：名稱與描述用來低成本篩選，適用條件用來裁決，詳細內容才是真正昂貴、只在需要時支付的部分。

此四欄位對應 Template_Set 中的 `skill-document.template.md` 樣板，其中名稱、描述、適用條件對應 metadata 區塊，詳細內容對應「適用場景 / 專案慣例 / 常見陷阱」等章節。

> **參考範例（非規格要求）｜工具：含 YAML front matter 的 SKILL.md**
>
> 四欄位在某些工具中可能落地為一份 `SKILL.md`：以 YAML front matter 承載 `name` 與 `description`，以正文標題承載適用場景、專案慣例與常見陷阱。front matter 的具體語法是工具落地細節，非本規格對四欄位的表達要求；規格層僅要求四個欄位齊備且名稱與描述可在不載入詳細內容時被讀取。

### 4.2 漸進式披露（Progressive Disclosure）載入規則

Skill_Document 的載入**必須**遵循漸進式披露原則：

1. **預設狀態**：代理啟動或評估工作時，對每一份 Skill_Document **僅載入名稱與描述**兩個欄位，不載入適用條件的裁決結果之外的詳細內容。此時代理只知道「有這樣一份技能存在、它大致關於什麼」，尚未支付詳細內容的上下文成本。
2. **載入裁決**：代理依名稱與描述初步篩選出可能相關的技能後，比對該技能的**適用條件**與當前工作情境。**唯有適用條件成立時**，才載入該技能的詳細內容。
3. **適用條件不成立**：若適用條件不成立，代理**不得**載入該技能的詳細內容，該技能維持在僅名稱與描述的輕量狀態。

此規則確保上下文成本與實際需求對齊：無關的技能永遠停在輕量層，只有真正適用的技能才展開為完整內容。詳細內容的載入是**由適用條件閘控**的，而非預設全載或憑代理主觀判斷全載。

> 與成本控管的關聯：漸進式披露是控制每次 Loop 執行上下文成本的手段之一；相關的成本與風險控管標準見第 11 章。

### 4.3 多 Skill_Document 的索引清單要求

當使用者的專案含有**多個** Skill_Document 時，本規格**要求建立一份索引清單**，記錄每一份 Skill_Document 的**名稱**與**適用場景**：

| 索引欄位 | 說明 |
| --- | --- |
| 名稱 | 對應該 Skill_Document 的名稱欄位，於專案內唯一 |
| 適用場景 | 摘述該 Skill_Document 的適用條件，說明「什麼情況下應載入此技能」 |

索引清單是漸進式披露在多技能情境下的運作基礎：代理透過索引清單，才能在**不逐一開啟每份技能詳細內容**的前提下，綜覽全部可用技能並依適用場景挑選出應進一步評估載入的技能。索引清單本身屬於輕量識別層，應可低成本常駐。

### 4.4 索引清單缺失時的行為

若專案含有**多個** Skill_Document **但索引清單缺失**，本規格**判定 Skill_Document 功能不得運作**，直到索引清單建立完成為止：

- 在索引清單缺失期間，代理**不得**依賴 Skill_Document 機制載入任何技能的詳細內容。
- 此判定的理由是：缺少索引清單時，代理無從在不逐份展開的情況下得知有哪些技能、各自適用於何種場景，漸進式披露的篩選基礎不存在，將退化為「全載」或「憑主觀猜測載入」，違反本章的漸進式披露原則。
- 恢復條件為：建立涵蓋所有 Skill_Document 之名稱與適用場景的索引清單後，Skill_Document 功能方可運作。

此規則僅在專案含有多個 Skill_Document 時生效；單一 Skill_Document 的情境不強制索引清單。此行為判定以抽象語言描述「缺索引則停用」的運作規則，不綁定任何工具的檔案格式或載入介面。

## 5. Connector（外部連接器）

Connector 是讓 Loop 存取**外部系統**的機制，例如問題追蹤系統、CI 系統、通訊工具或其他資料來源。它回答「當閉環需要的資訊或動作落在自身無法直接觸及的系統時，該如何安全且可追溯地接上去」。一個 Loop 的六階段（發現、分類、分配、驗證、記錄）常需要來自專案外部的輸入或對外部系統的寫入；Connector 就是承載這類跨系統存取的組件。本章以工具無關的抽象語言定義 Connector 的**使用決策標準**與**記錄要求**：任何能標準化描述外部能力與存取範圍的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 5.1 是否需要 Connector 的決策標準

判斷一個 Loop 是否需要 Connector，依據下列標準：

> **決策標準**：當 Loop 需要存取其**自身無法直接讀寫**的外部資料來源或系統時，**須使用 Connector**。

據此標準展開的判斷方式：

- **需要 Connector 的情況**：Loop 所需的資料或所要執行的動作，位於閉環自身執行環境**之外**、無法以既有的檔案系統或工作空間存取觸及者。例如：讀取問題追蹤系統中的問題單、查詢 CI 系統的工作狀態、向通訊工具發送通知、呼叫外部服務的 API。這些皆屬「自身無法直接讀寫」的外部系統，須透過 Connector 接入。
- **不需要 Connector 的情況**：Loop 所需的一切皆可在其自身可直接讀寫的範圍內完成者（例如僅讀寫專案內檔案、Memory_File、Isolated_Workspace 內的內容），不需引入 Connector。為外部存取而生的組件不應被用於本可直接完成的工作，以免徒增存取面與風險。

此標準的核心是「**可直接讀寫與否**」這條界線：界線之內由 Loop 自身處理，界線之外才動用 Connector。

### 5.2 MCP 為主要參考標準（建議而非強制）

本規格以 **MCP（Model Context Protocol）** 作為 Connector 的**主要參考標準**：當需要為 Loop 接入外部系統時，MCP 是本規格推薦優先考慮的標準化協議，因其以一致的方式描述外部工具、資源與其能力，有利於跨工具重用同一套外部連接設計。

然而，**MCP 為建議採用而非強制採用**：

- 本規格**推薦**優先採用 MCP 作為 Connector 的實現協議，但**不強制**任何 Loop 必須使用 MCP。
- 使用者**得**依專案實際情況選用非 MCP 的 Connector 機制（例如既有的 REST/gRPC 用戶端、專用 SDK、自訂整合層等），此選擇**不違反**本規格。
- 選用非 MCP 機制時，須遵循 5.3 的記錄要求，以維持與 MCP 標準相當的可追溯性。

換言之，MCP 是**參考基準與建議首選**，而非合規門檻；規格層在意的是 Connector 被**充分記錄且存取範圍明確**，而非其底層採用哪一種協議。

> **參考範例（非規格要求）｜工具：MCP server／client**
>
> 在採用 MCP 的落地中，外部系統可能以一個 MCP server 暴露其工具與資源，Loop 端以 MCP client 連接並依協議查詢可用能力。server/client 的具體設定與協議細節屬工具落地細節，非本規格對 Connector 的表達要求；規格層僅要求：需要外部存取時使用 Connector（5.1）、優先考慮 MCP 但不強制（5.2）、非 MCP 機制須同時記錄能力清單與存取範圍（5.3）。

### 5.3 非 MCP 機制的記錄要求：能力清單與存取範圍

當使用者實際採用**非 MCP** 的 Connector 機制時，本規格**要求在該 Connector 可被使用之前，同時記錄下列兩者**：

| 記錄項目 | 說明 |
| --- | --- |
| **能力清單（capability list）** | 該 Connector 能做什麼：可呼叫的操作、可讀取或寫入的資源類型、提供的功能項目 |
| **存取範圍（access scope）** | 該 Connector 能觸及到多大範圍：可存取哪些外部系統、哪些資源、讀取或寫入權限的邊界 |

此要求的合規條件為**兩者兼備**：

- **不接受僅記錄其中一項的部分文件**。僅記錄能力清單而缺存取範圍，或僅記錄存取範圍而缺能力清單，皆**不符合**本要求，該 Connector **不得**被 Loop 使用，直到兩者皆記錄完成。
- 記錄須在該 Connector **可被使用之前**完成，而非事後補記；未同時記錄能力清單與存取範圍者，視為尚不可用。
- 之所以兩者缺一不可：能力清單回答「它能做什麼」，存取範圍回答「它能碰到多大範圍」，唯有兩者並存才能完整評估此 Connector 的作用與風險面，維持與 MCP 標準化描述相當的可追溯性。

能力清單與存取範圍對應 Template_Set 中的 `connector-registry.template.md` 樣板：使用者於該樣板逐一登錄每個 Connector 的名稱、用途、存取範圍與所屬 Loop，作為「可被使用之前已完成記錄」的落地依據。此記錄要求以抽象語言描述「用前先記錄能力與範圍」的規則，不綁定任何工具的連接設定格式或介面。

## 6. Sub_Agent_Role（子代理角色）

Sub_Agent_Role 是一個 Loop 內部分工的代理角色。它回答「在這個閉環裡，是誰、以什麼職責、能碰到哪些檔案來完成某一類工作」。一個 Loop 常需要多種性質不同的工作交錯進行：有的工作**產出**新的結果（探索、實作、寫測試），有的工作**審查**既有結果是否可信。若讓同一個代理既產出又審查自己的產出，會落入「自我審查的寬容偏差」——製造者傾向認可自己的成果，使審查形同虛設。Sub_Agent_Role 以**角色分工**與**製造/檢查分離**解決此問題。本章以工具無關的抽象語言定義子代理角色標準：任何能指派不同代理實例並限制其檔案存取權限的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 6.1 角色分類：製造者與檢查者

每一個 Sub_Agent_Role **必須**歸屬於下列兩大分類之一：

1. **製造者角色（Producer）**：**產出**結果的角色。其工作會產生新的或修改後的產物——例如探索並回報發現、撰寫或修改程式碼、撰寫或執行測試。製造者角色是閉環中「讓事情往前推進」的一方。
2. **檢查者角色（Checker）**：**審查**結果的角色。其工作是對製造者的產出進行客觀查核，判斷是否滿足 Loop 的 Verification_Condition（見第 8 章），而**不**產出待審查的成果本身。檢查者角色是閉環中「守住品質底線」的一方。

此兩類分類描述的是**角色相對於產出的立場**（製造 vs 審查），與使用哪種工具無關。本規格的四個預設角色依此分類歸屬如下（完整樣板見 Template_Set 中的 `sub-agent-role.template.md`）：

| 預設角色 | 分類 | 一句話職責 |
| --- | --- | --- |
| **Explorer** | 製造者 | 探索程式碼與情境，回報發現（唯讀，見 6.4） |
| **Implementer** | 製造者 | 撰寫或修改程式碼以實作工作項目 |
| **Tester** | 製造者 | 撰寫或執行測試以產生驗證證據 |
| **Reviewer** | 檢查者 | 審查產出是否滿足 Verification_Condition（唯讀，見 6.4） |

> 分類與存取權限是兩個獨立面向：製造者不必然可寫（Explorer 屬製造者卻為唯讀），檢查者恆為唯讀。分類回答「立場」，存取權限回答「能碰到什麼」（見 6.3、6.4）。

### 6.2 產出與審查任務須分派給不同角色實例

當一個 Loop **同時包含產出結果與審查結果兩種任務**時，本規格**要求該 Loop 將產出任務與審查任務指派給不同的 Sub_Agent_Role 實例**，不得由同一個實例兼任兩者：

- **不同實例**：負責產出某項結果的角色實例，與負責審查該結果的角色實例，**必須是兩個不同的實例**。同一個實例不得既製造某產物又審查同一產物——這正是要避免的自我審查寬容偏差。
- **允許同一角色類型的不同實例**：本規則要求的是「不同**實例**」，而非「不同**角色類型**」。允許同一種角色類型於不同實例下分別承擔產出與審查工作。例如兩個各自獨立的實例可同屬某一角色類型，一個實例負責製造、另一個實例負責檢查該產物；重點在於**製造者實例與檢查者實例不是同一個**，而非兩者必須是不同名稱的角色。
- 此規則與第 8 章 Verification_Condition 的角色分離要求（負責檢查完成條件的角色不得與產出待驗證結果的角色為同一者）一致，兩章互相呼應。

此分離規則以抽象語言描述「製造與審查不可同體」，不綁定任何工具的子代理呼叫語法；使用者只要在目標機制中以兩個獨立的代理實例分別執行產出與審查，即符合本要求。

> **參考範例（非規格要求）｜工具：具子代理呼叫的 agent 平台**
>
> 在支援分派子代理的工具中，製造與審查分離可能落地為：先呼叫一個子代理實例執行 Implementer 職責產出變更，再呼叫**另一個獨立的**子代理實例執行 Reviewer 職責審查該變更。兩次呼叫產生兩個不同實例是關鍵；具體的子代理呼叫 API 與參數屬工具落地細節，非本規格對「不同實例」的表達要求。

### 6.3 每角色的記錄要求：職責範圍、輸入/輸出、存取權限

針對 Loop 中的**每一個** Sub_Agent_Role，本規格**要求記錄**下列三項，缺一不可：

| 記錄項目 | 說明 |
| --- | --- |
| **職責範圍（responsibility）** | 此角色負責哪一類工作、其工作邊界到哪裡；界定「它該做什麼、不該做什麼」 |
| **輸入 / 輸出（input / output）** | 此角色接收什麼作為輸入（例如工作項目、待審查產物、Memory_File 章節），產出什麼作為輸出（例如程式碼變更、測試結果、審查意見） |
| **存取權限（access）** | 此角色對檔案的存取層級，取值為**唯讀（read-only）**或**可寫（read-write）**；界定它能否修改檔案 |

三項記錄的意義：

- **職責範圍**確保角色分工明確，避免職責重疊或空白。
- **輸入/輸出**讓角色間的銜接可追溯——一個角色的輸出往往是另一角色的輸入（例如 Implementer 的輸出是 Reviewer 的輸入）。
- **存取權限**是安全與正確性的邊界：唯讀角色不得修改檔案，可寫角色才可修改。此項也是 6.4 唯讀標示的依據。

此三項對應 Template_Set 中的 `sub-agent-role.template.md` 樣板，使用者可於樣板中為每個角色逐項填寫角色名稱、職責範圍、輸入/輸出、存取權限與製造者/檢查者分類。Memory_File（第 7 章）中的進行中事項亦應記錄負責的 Sub_Agent_Role，以維持「哪個角色在做哪件事」的可追溯性。

### 6.4 Explorer 與 Reviewer 標示為唯讀

本規格將 **Explorer** 與 **Reviewer** 兩個角色的存取權限**標示為唯讀（read-only）**：

- **Explorer（唯讀製造者）**：其工作**僅限讀取與回報發現**，例如閱讀程式碼、蒐集情境、彙整觀察結果，**不得修改程式碼**或任何專案檔案。Explorer 產出的是「發現與回報」這類資訊產物，而非對檔案的寫入。
- **Reviewer（唯讀檢查者）**：其工作**僅限讀取與回報審查結果**，例如檢視製造者的產出、比對 Verification_Condition、提出審查意見與核准/退回判斷，**不得修改程式碼**或任何專案檔案。Reviewer 若能改碼，將模糊製造與檢查的界線，違反 6.2 的分離原則。

此唯讀標示的意義：把 Explorer 與 Reviewer 的存取權限限制為唯讀，既降低了誤改檔案的風險面，也在制度上保證檢查者無法「一邊審查一邊順手改成通過」，維持審查的獨立性與可信度。相對地，Implementer 與 Tester 屬可寫角色，才被賦予修改程式碼或測試的權限。此唯讀規則對應 `sub-agent-role.template.md` 樣板中對 Explorer 與 Reviewer 存取權限欄位的預設值，並以抽象語言描述「哪些角色只能讀、不能寫」，不綁定任何工具的權限設定介面。

## 7. Memory_File（持久記憶檔）

Memory_File 是以 Markdown 或等價格式記錄 Loop **跨會話狀態**的持久檔案（例如 `AGENTS.md`、`TODO.md`、`PROGRESS.md`）。它回答「當代理在新會話中失去先前上下文時，要從哪裡讀回這個閉環已經做到哪、正在做什麼、還有什麼待辦」。AI 代理的上下文通常不跨會話保存；若不把狀態外部化為檔案，每次新會話都會遺失進度，閉環便無法可靠地重複執行。Memory_File 以**結構化的持久檔案**充當閉環的長期記憶：每輪執行把最新狀態寫回檔案，新會話再從檔案讀回，使 Loop 的六階段（發現、分類、分配、驗證、記錄）能跨會話銜接。本章以工具無關的抽象語言定義持久記憶檔標準：任何能承載結構化文字並跨會話保存的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 7.1 三區塊標準 Markdown 結構

每一份 Memory_File **必須**包含下列三個區塊，缺一不可：

| 區塊 | 說明 | 用途 |
| --- | --- | --- |
| **進行中事項（In Progress）** | 目前正在被處理、尚未完成的工作項目 | 讓新會話得知「閉環當下正在做什麼、由誰做、進行到哪」；每筆須依 7.3 記錄補充資訊 |
| **已完成事項（Done）** | 已完成並通過驗證的工作項目 | 保存進度軌跡，避免重複處理已完成的工作 |
| **待分類事項（Unsorted）** | 已被發現但尚未分類或指派的工作項目 | 承接發現階段產出、尚未進入分配的原始工作 |

三區塊對應閉環的工作流向：**待分類事項**承接「發現」階段的原始產出，經「分類／分配」後成為**進行中事項**，通過「驗證」後移入**已完成事項**。此結構讓任一會話都能從單一檔案綜覽「還沒分類的、正在做的、已完成的」三種狀態，無須依賴會話內記憶。

此三區塊結構對應 Template_Set 中的 `memory-file.template.md` 樣板，使用者可直接於樣板中依區塊填寫。

> **參考範例（非規格要求）｜工具：Markdown 任務清單**
>
> 三區塊在 Markdown 中可能以三個標題（如 `## 進行中事項`、`## 已完成事項`、`## 待分類事項`）承載，各區塊內以任務清單語法（`- [ ]` 未完成、`- [x]` 已完成）逐條列出工作項目。標題文字與清單語法屬檔案落地細節，非本規格對三區塊的表達要求；規格層僅要求三個區塊齊備且語意對應「進行中／已完成／待分類」。

### 7.2 每輪執行後更新任務狀態

**當一個 Loop 完成一輪任務執行時**，本規格**要求該 Loop 將任務狀態更新至對應的 Memory_File**：

- 每輪執行結束後，須把該輪造成的狀態變化寫回 Memory_File，使檔案內容反映最新進度。狀態變化包含但不限於：新發現的工作進入**待分類事項**、已分類／指派的工作由待分類移入**進行中事項**、通過驗證的工作由進行中移入**已完成事項**。
- 更新是**每輪執行後皆須進行**的動作，而非累積數輪才寫一次。此要求確保 Memory_File 始終是「截至上一輪為止」的權威狀態來源，讓後續任一會話讀回時得到一致、最新的進度。
- 此更新對應閉環六階段中的「記錄（record）」階段：一輪執行的收尾即是把結果寫回至少一個 Memory_File。

此要求以抽象語言描述「每輪執行後把狀態寫回持久檔」，不綁定任何工具的檔案寫入指令或介面。

### 7.3 進行中事項的記錄要求

針對 Memory_File 中的**每一個進行中事項**，本規格**要求記錄**下列三項：

| 記錄項目 | 說明 |
| --- | --- |
| **負責的 Sub_Agent_Role** | 此進行中事項由哪個 Sub_Agent_Role 負責（見第 6 章）；界定「這件事現在是誰在做」 |
| **所屬 Isolated_Workspace（若有使用）** | 此事項的工作在哪個 Isolated_Workspace 中進行（見第 3 章）；**若該事項未使用隔離工作空間，則此項可省略** |
| **Verification_Condition 達成狀態** | 此事項目前對其 Verification_Condition（見第 8 章）的達成情形，例如尚未驗證、部分達成、已達成 |

三項記錄的意義：

- **負責的 Sub_Agent_Role** 讓「哪個角色在做哪件事」可追溯，與第 6 章的角色記錄要求呼應；新會話讀回時即知該事項的負責角色。
- **所屬 Isolated_Workspace** 讓「該事項的變更落在哪個隔離工作空間」可追溯，與第 3 章多角色並行時的獨立工作空間規則呼應；此項為**條件性**——僅在該事項確實使用了 Isolated_Workspace 時才須記錄，未使用者可省略。
- **Verification_Condition 達成狀態** 讓「這件事離完成還有多遠」一目了然，作為判斷是否可移入已完成事項的依據，與第 8 章的客觀化驗證條件呼應。

此三項記錄僅要求施加於**進行中事項**；已完成事項與待分類事項不強制此三項記錄。三項記錄對應 `memory-file.template.md` 樣板中進行中事項區塊的欄位，並以抽象語言描述「進行中事項該附記哪些追溯資訊」，不綁定任何工具的檔案格式或欄位語法。

## 8. Verification_Condition（客觀化驗證條件）

Verification_Condition 是用於**客觀判定**一個 Loop 的任務是否完成或應停止的條件（於 `loop.yaml` 對應 `verify` 階段內的停止條件）。它回答「這個閉環憑什麼宣告某件事已經做完、可以移入已完成事項或停止重試」。若完成與否僅憑代理或使用者的主觀感覺（「看起來差不多了」「應該沒問題」），閉環將在無明確依據下自我宣告成功，產出不可信且無法自動化判定；一旦這類主觀判斷被寫進會自動重複執行的 Loop，錯誤會被無聲地放大。Verification_Condition 以**可客觀檢查的判準**取代主觀判斷：任一具備判定能力的角色，依同一條件檢查同一產物，都應得到相同的通過或不通過結果。本章以工具無關的抽象語言定義驗證條件標準：任何能對產出施加可重複、可查核判準的機制，皆可依此標準實現，而無須改寫本章的規格要求。

### 8.1 每個 Loop 至少一個 Verification_Condition

每一個 Loop **必須**定義**至少一個** Verification_Condition，作為該 Loop 任務**完成或停止的判定依據**：

- 沒有任何 Verification_Condition 的 Loop 缺乏客觀的收斂條件——它無從判斷「工作已達標可完成」或「已無進展應停止」，只能無限重試或憑主觀喊停，兩者皆不可接受。
- Verification_Condition 同時服務兩種判定：**完成判定**（產出滿足條件，可移入已完成事項，見第 7 章）與**停止判定**（在達成或明確無法達成時終止該輪，避免空轉，成本考量見第 11 章）。
- 一個 Loop 可定義多個 Verification_Condition；本條要求的是**下限為一**，且每個條件皆須符合 8.2 的客觀性要求與 8.3 的可驗證類型。

此要求對應閉環六階段中的「驗證（verify）」階段：該階段至少承載一個可客觀檢查的完成/停止條件，Loop 才具備自動判定收斂的能力。

### 8.2 主觀條件不合規，須改寫為可客觀驗證條件

若一個 Verification_Condition 的描述**僅為主觀判斷**而非可客觀檢查的標準，本規格**判定該條件不合規**，並**要求改寫為可客觀驗證的條件**：

- **判定原則**：一個條件是否客觀，取決於「不同角色依此條件檢查同一產物是否會得到一致結果」。若條件的成立與否取決於檢查者的個人感受、審美或未定義的模糊程度副詞（「差不多」「大致上」「品質良好」），則其結果因人而異，**判定為不合規的主觀條件**。
- **改寫要求**：不合規的主觀條件不得沿用，必須改寫為可客觀驗證的條件——把模糊描述替換為可重複檢查的判準（見 8.3 的類型清單），使條件的通過與否有明確、可查核的依據。

下表以**合規 vs 不合規對照**說明改寫方向：

| 不合規（主觀，結果因人而異） | 合規（可客觀驗證，結果一致可查核） |
| --- | --- |
| 「程式碼品質看起來不錯」 | 「靜態檢查（lint）零錯誤、零警告」 |
| 「測試應該都有過」 | 「指定測試套件全部通過，無失敗與略過」 |
| 「效能大致可接受」 | 「關鍵路徑 p95 延遲 ≤ 200ms（指標達門檻）」 |
| 「文件寫得差不多了」 | 「六大組件章節皆存在且非空，經檢查者角色核准」 |
| 「這個 bug 感覺修好了」 | 「原可重現失敗的測試案例現已通過，且未新增失敗」 |

改寫的核心動作：把「感覺／看起來／應該」這類主觀措辭，替換為「哪個可檢查對象、達到哪個可量測或可核准的判準」。凡無法轉為此形式者，代表該完成條件本身尚未想清楚，應先釐清再納入 Loop。

### 8.3 可客觀驗證條件的範例類型清單

本規格提供下列可客觀驗證條件的**範例類型清單**，作為撰寫合規 Verification_Condition 的參考。此清單**至少包含**下列四種類型（為非窮舉清單，其他同樣可重複查核的判準亦可採用）：

| 類型 | 判定方式 | 抽象範例（非工具語法） |
| --- | --- | --- |
| **測試全部通過** | 指定的測試集合執行後全數通過，無失敗、無錯誤 | 「所指定的測試套件全部通過」 |
| **靜態檢查（lint）無錯誤** | 靜態檢查工具對指定範圍執行後回報零錯誤 | 「靜態檢查在指定規則集下零錯誤」 |
| **指標達到指定門檻** | 某可量測數值指標達到事先約定的門檻 | 「覆蓋率 ≥ 80%」「p95 延遲 ≤ 200ms」 |
| **檢查者角色核准** | 由與製造者分離的檢查者角色（見 8.4、第 6 章）依明確準則核准 | 「Reviewer 依審查準則核准通過」 |

前三類（測試、靜態檢查、指標門檻）為**機器可判定**的判準：由自動化執行得出一致結果，最適合作為 Loop 的客觀收斂依據。第四類（檢查者角色核准）為**角色可判定**的判準，用於難以完全自動量化、但仍須客觀查核的產出；其客觀性由「依明確準則審查」與「製造/檢查角色分離」（8.4）共同保障，而非取決於檢查者的主觀好惡。

> **參考範例（非規格要求）｜工具：泛用測試與靜態檢查器**
>
> 「測試全部通過」在某些工具中可能落地為執行某測試指令並要求其結束碼為 0，「靜態檢查無錯誤」可能落地為執行某 lint 指令並要求零錯誤輸出。具體指令名稱與結束碼判讀屬工具落地細節，非本規格對驗證條件的表達要求；規格層僅要求條件本身可被客觀、可重複地查核。

### 8.4 檢查者與製造者不可為同一角色

本規格**要求**：負責**檢查** Verification_Condition 的 Sub_Agent_Role，與負責**產出待驗證結果**的 Sub_Agent_Role，**不可為同一角色**：

- 判定某產出是否滿足 Verification_Condition 的工作，必須由**與產出該結果者不同**的角色實例執行。讓製造者檢查自己的產物，等同自我審查，會落入認可自身成果的寬容偏差，使 Verification_Condition 形同虛設。
- 此要求與第 6 章 6.2「產出與審查任務須分派給不同角色實例」**一致並互相呼應**：6.2 要求製造與審查由不同實例承擔（允許同一角色類型的不同實例），本條從 Verification_Condition 的角度重申同一原則——**檢查完成條件者不得是產出待驗證結果者**。
- 落地上，這通常表現為由檢查者角色（如 Reviewer，唯讀，見 6.4）負責比對 Verification_Condition 並作出核准/退回判斷，而製造者角色（如 Implementer、Tester）僅負責產出；此分離亦是第 3 章 3.4「合併回主線前的驗證步驟」中「由檢查者角色審查」一項的判定基礎。

此分離規則以抽象語言描述「驗證條件的裁決者與產出者必須分離」，不綁定任何工具的角色指派或審查介面；使用者只要確保檢查 Verification_Condition 的角色實例不同於產出待驗證結果的角色實例，即符合本要求。

## 9. 設計原則檢查清單

設計原則檢查清單是設計**新** Loop 時逐項確認的一份判斷依據。它回答「當我把一段工作交給會自動重複執行的閉環時，如何確保人仍然握有對產出的驗證責任與理解力，而不是把判斷力也一併外包出去」。自動化的價值在於讓人從逐條提示中解放，但同一股力量若無節制，會把「人該保留的判斷」也一併吞掉：驗證責任悄悄轉移給機器、對產出逐漸看不懂、最終對閉環的一切照單全收。這三種滑坡不是技術缺陷，而是**設計取向**的偏差，無法靠 Validator 之類的機器檢查捕捉，只能靠設計者在設計當下自我提問。本章以工具無關的抽象語言列出至少三項設計原則，並為每項原則附上至少一個**自我檢查判斷問題**：設計新 Loop 時逐題自問，答案若偏離原則，即應在啟用前調整設計。本章對應 Template_Set 中的 `design-principles-checklist.template.md` 樣板，使用者可將下列原則與問題作為勾選清單，於設計每個新 Loop 時逐項確認。

> 定位說明：本章（設計原則）用於**設計新 Loop 時**的正向自我檢查；第 10 章（反模式）用於**審查既有 Loop 時**的負向比對。兩者互補——前者問「我是否守住了該守的原則」，後者問「我是否踩到了該避的模式」。

### 9.1 三項設計原則

每個新 Loop 的設計**應**通過下列三項原則的檢視。三項原則彼此關聯：驗證責任歸屬於人是底線，保持對產出的理解力是維持該底線的前提，避免認知投降則是防止前兩者被自動化便利性侵蝕的態度。

1. **驗證責任歸屬於人（Verification responsibility belongs to humans）**

   閉環可以自動產出、自動依 Verification_Condition（見第 8 章）判定完成，但「**這個閉環整體是否值得信任、產出是否真的達標**」的最終責任，始終歸屬於設計與運行它的人，不因自動化而轉移給機器。Verification_Condition 讓完成判定變得客觀且可自動化，但它驗證的是「產出是否符合**我事先定義的條件**」；至於「這些條件本身是否足夠、是否涵蓋了真正重要的面向」，仍是人的責任。這項原則要求設計者把 Verification_Condition 視為**自己驗證意圖的延伸**，而非可以取代自己判斷的替身——機器負責重複執行客觀判準，人負責確保這些判準確實對應到自己願意背書的品質標準。與第 6、8 章的製造/檢查分離呼應：分離避免的是自我審查偏差，本原則守住的是「連檢查者角色的核准，最終仍由人負責認定其可信」這條底線。

2. **保持對產出的理解力（Maintain comprehension of output）**

   設計者**應**始終保持對 Loop 產出的理解力：能看懂閉環產生了什麼、為什麼這樣產生，以及在需要時能親自查核而不只依賴閉環自身的通過報告。當 Loop 高頻自動產出、產物累積速度超過人能理解的速度時，理解力會悄悄流失——人開始只看「綠燈/紅燈」而不看內容，逐漸失去對產出實質的掌握。喪失理解力的代價是：一旦閉環出錯，設計者既無法及早察覺，也無力診斷與修正，因為他已不理解閉環在做什麼。這項原則要求 Loop 的設計刻意保留人可理解的檢查點——例如透過 Memory_File（見第 7 章）留下可讀的進度與決策軌跡、控制單輪產出規模、確保 Verification_Condition 的通過理由對人是可解讀的——使理解力不隨自動化程度上升而下降。

3. **避免認知投降（Avoid cognitive surrender）**

   設計者**應**避免「認知投降」——即因為閉環大多時候運作良好，就停止思考、對其產出與判定一律照單全收，把本該由自己保留的判斷力也交給機器。認知投降是前兩項原則失守後的終點狀態：驗證責任已默認轉移、對產出已不再理解，於是設計者對閉環的信任從「經查核的信任」退化為「無條件的信任」。這種投降特別危險，因為它發生得無聲無息且看似合理（「它一直都對，何必費心檢查」），而自動重複執行會把此期間累積的任何錯誤無聲放大。這項原則要求設計者在設計時就預留**保持懷疑的機制**——例如定期抽查產出、對高風險輸出要求人工確認、不讓任何 Loop 在完全無人過問下長期運行——使「持續思考與查核」成為 Loop 運行的常態，而非可被便利性豁免的選項。

### 9.2 各原則的自我檢查判斷問題

下列自我檢查判斷問題對應 9.1 的三項原則，設計新 Loop 時**應**逐題自問。每項原則至少附一個判斷問題；若任一問題的誠實答案偏離該原則的方向，即代表此 Loop 的設計尚未通過該原則，應在啟用前調整。此清單對應 `design-principles-checklist.template.md` 樣板，可作為勾選項逐條確認。

| 對應原則 | 自我檢查判斷問題 |
| --- | --- |
| 驗證責任歸屬於人 | 我是否清楚這個 Loop 的每一項 Verification_Condition 在驗證什麼，並確認這些條件足以讓我**願意為其產出背書**？是否存在「我沒真正想清楚、只是先放著讓機器判定」的完成條件？ |
| 驗證責任歸屬於人 | 如果這個 Loop 的產出日後出了問題，我能否說清楚「當初是依據哪些條件判定它通過的」，而不是把責任推給「是自動化判斷的」？ |
| 保持對產出的理解力 | 對於這個 Loop 每一輪的產出，我是否**仍看得懂它做了什麼、為什麼這樣做**？單輪產出的規模是否已超過我能實際查核的程度？ |
| 保持對產出的理解力 | 這個 Loop 是否在 Memory_File 或等價處留下了**人可讀**的進度與決策軌跡，讓我在任一會話都能重建對閉環狀態的理解，而不只依賴它自己回報的通過/失敗？ |
| 避免認知投降 | 我是否設計了**定期抽查或人工確認**的機制，讓自己不會因為「它一直都對」就停止查核？這個 Loop 是否可能在完全無人過問的情況下長期運行？ |
| 避免認知投降 | 對於這個 Loop 中**風險較高**的輸出（例如會合併回主線、對外發送、或難以復原的動作），我是否要求在自動判定之外仍有人保持懷疑並介入確認？ |

上述問題以抽象語言描述「設計者該對自己提出的判斷」，不綁定任何工具的設定或介面；使用者只要在設計每個新 Loop 時逐題自問並依答案調整設計，即符合本章要求。凡無法對某題給出符合原則方向的誠實答案者，代表此 Loop 在該原則上仍有設計缺口，應先補足再啟用。

## 10. 反模式檢查清單

反模式檢查清單是審查**既有** Loop 時逐項比對的一份負向判斷依據。它回答「一個已經設計好、甚至已在運行的閉環，是否踩到了會在造成實際損害前就該被發現的常見錯誤模式」。第 9 章的設計原則清單用於設計新 Loop 時的正向自我提問，本章則相反：假設 Loop 已經存在，把它拿來對照一份**已知會出事的模式清單**，逐項檢查「我這個 Loop 是否正表現出這些症狀」。這類反模式（Anti_Pattern）不是語法錯誤（那由第二層的 Validator 捕捉），而是**設計層面的壞味道**——它們在短期內往往看似正常運作，卻在自動重複執行下逐步累積成本、放大錯誤或侵蝕產出可信度。本章以工具無關的抽象語言列出至少三項 Anti_Pattern，並為每一項描述**可觀察的症狀**（review 時憑什麼認出它）與**對應的改善建議**（認出後該怎麼修）。本章對應 Template_Set 中的 `anti-pattern-checklist.template.md` 樣板，使用者可將下列 Anti_Pattern 與其症狀、改善建議作為比對清單，於審查每個既有 Loop 時逐項勾稽。

> 定位說明：本章（反模式）用於**審查既有 Loop 時**的負向比對；第 9 章（設計原則）用於**設計新 Loop 時**的正向自我檢查。兩者互補——設計時問「我是否守住了該守的原則」（第 9 章），審查時問「我是否踩到了該避的模式」（本章）。兩份清單可搭配使用：新 Loop 啟用前先過設計原則清單，運行一段時間後再定期以本章反模式清單回頭體檢。

### 10.1 三項 Anti_Pattern

本規格列出下列**至少三項** Anti_Pattern，作為審查既有 Loop 時必比對的最低集合（為非窮舉清單，團隊可依經驗補充其他反模式）。三者各自對應閉環的一個常見失守面向：複雜度失控、驗證失效、成本失管。

| Anti_Pattern | 一句話定義 | 為何有害 |
| --- | --- | --- |
| **Loop 過度複雜（Overly complex Loop）** | 單一 Loop 承擔過多職責、掛載過多 Sub_Agent_Role 或階段邏輯過度纏繞，使整個閉環難以被人理解與維護 | 過度複雜的 Loop 難以推理、難以除錯，一旦出錯不易定位；角色與交互越多，並行覆蓋與職責重疊的風險越高，也直接侵蝕第 9 章「保持對產出的理解力」的底線 |
| **Verification_Condition 過弱（Weak verification condition）** | Loop 的驗證條件形同虛設——或為主觀描述、或雖客觀但判準寬鬆到幾乎必然通過，無法真正攔截不合格產出 | 過弱的驗證條件讓閉環在「看似有驗證」的假象下持續放行劣質產出；因 Loop 會自動重複執行，這些未被攔截的錯誤會被無聲放大（見第 8 章） |
| **忽視成本管理（Ignoring cost management）** | Loop 未設定或不追蹤成本／頻率上限，任其在高頻或無節制的 token 消耗下運行，缺乏超限時的處置機制 | 忽視成本管理會讓閉環在無人察覺下持續累積費用與資源消耗，尤其定時觸發的空轉執行會在無變化時仍反覆付費（見第 2、11 章） |

三項 Anti_Pattern 之間常互相牽引：過度複雜的 Loop 往往同時難以定義有效的 Verification_Condition，也更難估算與控制成本。因此審查時三項宜一併比對，而非只看單一項。

### 10.2 各 Anti_Pattern 的可觀察症狀與改善建議

下列針對 10.1 每一項 Anti_Pattern，分別列出**可觀察的症狀**（審查既有 Loop 時可據以辨識的外顯跡象）與**對應的改善建議**（辨識後的修正方向）。審查時逐項比對；凡命中某項的多數症狀，即應依其改善建議調整該 Loop。此清單對應 `anti-pattern-checklist.template.md` 樣板，可作為勾選項逐條稽核。

**Anti_Pattern 一：Loop 過度複雜**

| 面向 | 內容 |
| --- | --- |
| 可觀察的症狀 | Loop 掛載的 Sub_Agent_Role 數量偏多（例如超過建議上限，導致難以說清每個角色的邊界）；單一 Loop 同時處理多個彼此無關的目標；閉環六階段中某階段塞入大量條件分支或特例；設計者或團隊已無法用幾句話說清「這個 Loop 到底在做什麼、下一步會怎麼走」；Memory_File 的進行中事項長期堆積、角色與工作空間對應關係難以追溯。 |
| 對應的改善建議 | 將過度複雜的 Loop **拆分為多個各自單一職責的較小 Loop**，每個只負責一個可清楚描述的目標；控制 Sub_Agent_Role 數量在建議上限以內（角色數上限見**第 6 章**），超限時精簡或合併角色；簡化各階段邏輯，把特例抽離為獨立 Loop 或前置條件；確保每個 Loop 都能以一兩句話說明其目的與收斂條件，以恢復第 9 章要求的「對產出的理解力」。 |

**Anti_Pattern 二：Verification_Condition 過弱**

| 面向 | 內容 |
| --- | --- |
| 可觀察的症狀 | 驗證條件使用主觀措辭（「看起來沒問題」「品質大致可接受」），不同人檢查同一產物會得到不同結論；驗證條件雖客觀但寬鬆到幾乎永遠通過（例如「至少有一個測試存在」而不要求其通過）；Loop 幾乎從不因驗證失敗而停下或退回；由**產出者自己**檢查自己的產物（製造/檢查未分離）；「綠燈」頻繁出現但實際產出品質並未相應可信。 |
| 對應的改善建議 | 依**第 8 章**把主觀條件改寫為可客觀驗證的條件，並確保每個 Loop 至少一個 Verification_Condition 落在可機器判定或可由檢查者依明確準則核准的類型（測試全通過、靜態檢查無錯誤、指標達門檻、檢查者核准）；收緊寬鬆判準，使其真正能攔截不合格產出；落實製造者與檢查者**角色分離**（見第 6、8 章），杜絕自我審查的寬容偏差；定期抽查「通過」的產出，驗證驗證條件本身是否足夠。 |

**Anti_Pattern 三：忽視成本管理**

| 面向 | 內容 |
| --- | --- |
| 可觀察的症狀 | Loop 未設定成本／token／頻率上限（`budget` 缺失或未追蹤）；高頻定時觸發在無變化時仍反覆空轉執行；缺乏超限時的處置機制（超過上限後仍照常執行、無告警、無降頻）；成本或 token 消耗持續上升卻無人監看；全程使用高階強推理模型處理本可由輕量模型完成的例行工作。 |
| 對應的改善建議 | 依**第 11 章**為 Loop 明確設定並記錄成本／token／頻率上限（`budget`），並定義超限時的處置（暫停、降頻、告警）；優先採用**事件觸發**取代無條件定時觸發，使閉環僅在確有變化時執行以減少空轉（觸發類型見第 2 章）；採用第 11 章的模型分層策略，讓例行工作交由輕量模型、僅高難度環節動用強推理模型；建議低頻起步、依產出品質再逐步調整頻率。 |

上述症狀與改善建議以抽象語言描述「如何認出反模式、認出後如何修正」，不綁定任何工具的設定或介面；使用者只要在審查每個既有 Loop 時逐項比對症狀，並依對應改善建議調整設計，即符合本章要求。凡命中某項 Anti_Pattern 多數症狀者，代表該 Loop 已踩到該反模式，應在其造成更大實際損害前依改善建議修正。

## 11. 成本與風險控管標準

成本與風險控管標準回答「當一個閉環會自動、重複、可能無人看守地執行時，如何避免它在無聲無息中累積失控的執行次數與費用」。自動重複執行是 Loop 的價值來源，卻也是其成本風險的根源：每一輪執行都在消耗 token 與運算資源，而「自動」意味著沒有人為每一輪的花費把關。若不從設計層面預先設定成本控管，閉環可能在無變化時仍反覆空轉、以昂貴模型處理本可廉價完成的例行工作、或在超出預算後仍照常執行。本章以工具無關的抽象語言定義四項控管標準：模型分層策略（11.1）、執行頻率記錄與低頻起步建議（11.2）、成本／Token 上限與超限處理的記錄要求（11.3）、優先採用事件觸發的建議（11.4）。這些標準與第 2 章（Automation_Trigger 的觸發類型與成本取捨）、第 4 章（Skill_Document 漸進式披露的上下文成本控制）、第 6 章（Sub_Agent_Role 分類）、第 10 章（「忽視成本管理」Anti_Pattern）互相呼應，共同構成閉環的成本防線。本章對應 Template_Set 中的 `cost-risk-control.template.md` 樣板，使用者可將模型分層設定、執行頻率、成本上限、超限處理方式與觸發方式作為填空欄位逐項記錄。

### 11.1 模型分層策略：輕量 / 主力 / 強推理三層

本規格定義一套**模型分層策略**：依 Sub_Agent_Role（見第 6 章）的**任務性質**，將所需的模型量級分為下列三層，讓每一類工作交由**足夠但不過度**的模型量級處理，避免以昂貴的強推理模型執行本可由輕量模型完成的例行工作。

| 模型層級 | 適用的任務性質 | 說明 |
| --- | --- | --- |
| **輕量模型（lightweight）** | 機械性、規則明確、判斷成分低的例行工作 | 例如格式整理、依明確清單勾稽、樣板填寫、結構化資訊擷取等。這類工作有明確輸入輸出與可查核判準，不需深度推理，交由輕量模型即可，以最低成本完成 |
| **主力模型（workhorse）** | 一般開發工作，需一定理解與生成能力但非高難度推理 | 例如依既定慣例撰寫或修改程式碼、撰寫測試、彙整與回報發現等閉環中量最大的日常工作。主力模型在成本與能力間取得平衡，承擔閉環的多數執行量 |
| **強推理模型（strong-reasoning）** | 高難度、需深度推理或跨多重約束權衡的關鍵環節 | 例如複雜架構決策、艱難缺陷的根因分析、對高風險產出的嚴謹審查等。這類工作誤判代價高，值得動用最強、也最昂貴的模型，但應僅限於確實需要之處 |

**依 Sub_Agent_Role 任務性質對應模型層級的建議**（角色定義見第 6 章）：

| 預設角色（第 6 章） | 分類 | 建議模型層級 | 理由 |
| --- | --- | --- | --- |
| **Explorer** | 製造者（唯讀） | 輕量至主力模型 | 探索與回報發現多為資訊蒐集與彙整，任務性質偏機械；情境單純時用輕量模型，需綜合判讀時升至主力模型 |
| **Implementer** | 製造者 | 主力模型 | 依既定慣例撰寫或修改程式碼屬閉環量最大的日常工作，適合成本能力平衡的主力模型；僅在遇到高難度設計時才升級 |
| **Tester** | 製造者 | 輕量至主力模型 | 依明確判準撰寫或執行測試的規則性高，多數情況輕量模型足夠；測試設計較複雜時升至主力模型 |
| **Reviewer** | 檢查者（唯讀） | 強推理模型 | 審查是攔截不合格產出的最後一道關卡，誤放代價高（尤其對合併回主線或高風險輸出的產物），值得動用強推理模型以嚴謹比對 Verification_Condition |

此對應為**建議而非強制**：使用者應依實際任務難度調整——同一角色在簡單情境可降級、在高難度情境可升級。核心原則是**讓模型量級對齊任務的實際推理需求**，而非全程一律使用最強模型（那會造成第 10 章「忽視成本管理」中「以強推理模型處理例行工作」的反模式）。此分層以抽象語言描述「哪類工作配哪種量級的模型」，不綁定任何工具的模型名稱或設定介面；使用者只要在目標工具中把三個層級對應到實際可用的模型即可。

### 11.2 執行頻率記錄與低頻起步建議

本規格**要求每個 Automation_Trigger（見第 2 章）記錄其執行頻率**，並就頻率的設定方式提出建議：

- **記錄要求**：如第 2 章 2.2 所述，每個 Automation_Trigger 皆須記錄「執行頻率」欄位（定時觸發填時間規則對應的頻率，事件觸發亦須以預期事件次數估計頻率）。本章重申此要求並闡明其成本意義：**執行頻率是成本評估的核心輸入**——每一輪執行都消耗資源，頻率越高，單位時間的累積成本越高。缺少執行頻率記錄，就無從估算閉環的成本規模，也無法判斷是否需要調整。
- **低頻起步建議**：本規格**建議以低頻率起步，待觀察產出品質後再依需要逐步調整頻率**。理由是：新設計的 Loop 其產出品質與實際價值尚未經驗證，一開始就設定高頻率會在品質未確認前即大量消耗成本，且會加速放大任何尚未發現的設計缺陷（見第 8 章對「錯誤被自動重複執行無聲放大」的說明）。低頻起步讓使用者有機會在小成本下觀察每輪產出是否可信、Verification_Condition 是否有效攔截問題，確認品質穩定後再提高頻率，是風險與成本兼顧的做法。
- **依產出品質調整**：頻率調整的依據應是**產出品質**而非單純的處理速度需求——當低頻運行證明產出穩定可信時，可提高頻率以加快推進；當發現產出品質不穩或成本超出預期時，應降頻回退並先修正設計。

此要求與建議以抽象語言描述「頻率須被記錄、且宜由低而高依品質調整」，不綁定任何工具的排程設定；執行頻率的記錄對應 Template_Set 中 `cost-risk-control.template.md` 樣板的「執行頻率」欄位，並與第 2 章 `automation-trigger.template.md` 的執行頻率欄位一致對應。

### 11.3 成本／Token 上限與超限處理的記錄要求

當使用者為某個 Loop 設定執行成本或 Token 用量上限時，本規格**要求同時記錄下列兩者**：

| 記錄項目 | 說明 |
| --- | --- |
| **上限數值** | 該 Loop 所設定的執行成本上限或 Token 用量上限的具體數值（含單位，例如每輪 / 每日 / 每月的成本或 token 數上限） |
| **超出上限時的處理方式** | 當實際消耗達到或超過上限時，閉環應採取的處置，例如暫停執行、降低觸發頻率、發出告警通知、要求人工確認後才續行等 |

記錄要求說明：

- **兩者須並存**：僅記錄上限數值而未定義超限處理方式，等同「知道紅線在哪卻沒規定越線後怎麼辦」——閉環可能在超限後仍照常執行，上限形同虛設。唯有同時記錄「上限是多少」與「超限後怎麼處理」，成本上限才具備實際的攔截效力。此與第 10 章「忽視成本管理」反模式中「缺乏超限時的處置機制」的症狀直接對應。
- **與 `loop.yaml` 的 `budget` 欄位對應**：在實作層，此成本／頻率上限對應 `loop.yaml` 的 `budget` 欄位（Validator 要求 `budget` 為大於 0 的數值，見實作層需求）。`budget` 承載上限**數值**；超限處理方式則為本章要求一併記錄的控管策略。規格層在意的是「上限與超限處理皆被明確記錄」，`budget` 欄位是此記錄在可執行定義中的落地形式。
- **此為條件性要求**：本要求在使用者**確有設定**成本或 Token 上限時生效，規範「一旦設定就必須連同處理方式一起記錄」；其目的是杜絕「設了上限卻沒說超限怎麼辦」的半套控管。

此記錄要求對應 Template_Set 中 `cost-risk-control.template.md` 樣板的「成本上限」與「超限處理方式」欄位，並以抽象語言描述「設了上限就要連同超限處理一起記錄」，不綁定任何工具的計費或用量設定介面。

### 11.4 優先採用事件觸發以降低空轉執行

本規格**建議優先採用事件觸發（Event-based）而非固定高頻率的定時觸發（Schedule-based）**（兩種觸發類型的定義見第 2 章 2.1），以降低無變化時的空轉執行：

- **空轉成本問題**：固定高頻率的定時觸發**不論外部是否有變化都會啟動**閉環。當外部狀態未變時，這些執行往往無事可做卻仍完整消耗一輪的 token 與運算成本——即「空轉執行」。頻率越高，空轉造成的無謂成本越大（見第 2 章 2.1 的成本取捨提示）。
- **事件觸發的優勢**：事件觸發**僅在特定事件實際發生時**才啟動閉環，因此「有變化才執行、無變化不執行」，天然避免了無變化時的空轉成本。對「有變化才需要反應」性質的工作（例如程式碼推送後檢查、問題單建立後處理），事件觸發能以顯著更低的成本達成相同目的。
- **建議而非強制**：本規格**建議**在「有變化才需反應」的情境優先選用事件觸發；但對「不論是否有變化都需定期執行」的情境（例如每日彙整、週期性健檢），定時觸發仍是正確選擇。取捨原則是：**當工作的必要性取決於外部變化時，用事件觸發以省去空轉；當工作須週期性進行而與外部變化無關時，才用定時觸發**，且此時應搭配 11.2 的低頻起步以控制頻率。

此建議與第 10 章「忽視成本管理」反模式改善建議中「優先採用事件觸發取代無條件定時觸發」一致。此觸發方式的選擇對應 Template_Set 中 `cost-risk-control.template.md` 樣板的「觸發方式」欄位，並以抽象語言描述「優先事件觸發以省空轉」，不綁定任何工具的排程或事件機制；使用者只要在目標工具中依此原則選定觸發類型即可。

### 12.1 Example_Loop A：PR 審查與測試修復（事件觸發）

**情境**：當主線分支收到新的 Pull Request 時，自動探索變更、補齊或修復測試、並在合併前完成獨立審查。此案例展示「有變化才反應」的事件觸發搭配製造/檢查分離。

**四要素記錄：**

| 要素 | 內容 |
| --- | --- |
| **Automation_Trigger** | 觸發類型＝事件觸發；觸發條件＝主線分支有新的 PR 推送；執行頻率＝每次 PR 事件發生時（估計每日約 3–8 次） |
| **涉及的 Sub_Agent_Role** | Explorer（唯讀，製造者，探索 PR 變更與受影響範圍）、Implementer（可寫，製造者，補齊或修復測試）、Reviewer（唯讀，檢查者，審查是否達 Verification_Condition）。製造與檢查由**不同實例**承擔（見第 6 章 6.2） |
| **使用的 Memory_File** | `TODO.md`（記錄待處理與進行中的 PR 事項；進行中事項附負責角色、所屬 Isolated_Workspace 與 Verification 達成狀態）、`PROGRESS.md`（每輪執行後以 ISO 8601 時間戳逆序追加處理紀錄） |
| **Verification_Condition** | ①「指定測試套件全數通過，無失敗與略過」（測試全通過類）②「靜態檢查零錯誤、零警告」（lint 類）③「Reviewer 依審查準則核准通過」（檢查者核准類）。三者皆達成方可合併回主線 |

**其他涵蓋組件：**

- **Isolated_Workspace**：Implementer 於一個與主線隔離的獨立工作空間中修改測試，變更先侷限其中，通過上述 Verification_Condition 並經 Reviewer 核准後才合併回主線（見第 3 章 3.4）。
- **Connector**：Loop 需讀取 PR 內容與 CI 工作狀態，這些位於閉環自身無法直接讀寫的外部系統，故透過 Connector 接入（見第 5 章 5.1；建議優先考慮 MCP，見 5.2）。

### 12.2 Example_Loop B：週期性依賴健檢（定時觸發）

**情境**：每週定期掃描專案依賴的已知漏洞與過期版本，產出升級建議並在隔離空間試升級、跑測試，最後由檢查者角色審查。此案例展示「與外部變化無關、須週期性執行」的定時觸發，並涵蓋全部六大組件。

**四要素記錄：**

| 要素 | 內容 |
| --- | --- |
| **Automation_Trigger** | 觸發類型＝定時觸發；觸發條件＝每週一早上；執行頻率＝每週一次（依第 11.2 低頻起步建議，確認產出穩定後再考慮調整） |
| **涉及的 Sub_Agent_Role** | Explorer（唯讀，製造者，蒐集依賴清單與漏洞情報）、Implementer（可寫，製造者，於隔離空間試行版本升級）、Tester（可寫，製造者，執行回歸測試）、Reviewer（唯讀，檢查者，審查升級風險與結果）。角色數 4，未逾第 6/10 章建議上限 |
| **使用的 Memory_File** | `AGENTS.md`（進行中／已完成／待分類三區塊，記錄本輪健檢的進行中升級事項及其負責角色、Isolated_Workspace、Verification 達成狀態）、`PROGRESS.md`（逆序追加每週健檢摘要） |
| **Verification_Condition** | ①「依賴漏洞掃描回報零高風險（high／critical）漏洞」（指標達門檻類）②「升級後指定測試套件全數通過」（測試全通過類）③「Reviewer 核准該次升級」（檢查者核准類） |

**其他涵蓋組件：**

- **Isolated_Workspace**：版本升級屬高風險變更，Implementer 在獨立工作空間試升級，失敗可整份拋棄而不污染主線；通過驗證與審查後才合併（見第 3 章）。
- **Skill_Document**：本 Loop 載入一份「依賴升級慣例」Skill_Document（記錄本專案的鎖版策略、破壞性變更檢查點、常見升級陷阱），依漸進式披露原則，僅在適用條件成立時才載入詳細內容（見第 4 章）。
- **Connector**：需存取外部漏洞資料庫／安全掃描服務與套件登錄資訊，屬閉環自身無法直接讀寫的外部系統，透過 Connector 接入（見第 5 章）。

> **參考範例（非規格要求）｜工具：泛用 cron 排程器**
>
> 本案例的抽象觸發條件「每週一早上」在支援 cron 的排程機制中，可能寫成類似 `0 9 * * 1` 的五欄位運算式。此運算式屬工具落地細節，非本規格對觸發條件的表達要求；規格層僅要求記錄「觸發類型＝定時觸發、觸發條件＝每週一早上、執行頻率＝每週一次」（見第 2 章 2.2）。

### 12.3 Example_Loop C：問題單分類與知識文件更新（事件觸發）

**情境**：當問題追蹤系統建立新問題單時，自動探索相關程式碼與既有文件、分類問題、並在確認為可沉澱的專案知識時更新對應的 Skill_Document，最後由檢查者角色審查文件正確性。此案例展示 Connector 與 Skill_Document 的協作。

**四要素記錄：**

| 要素 | 內容 |
| --- | --- |
| **Automation_Trigger** | 觸發類型＝事件觸發；觸發條件＝問題追蹤系統建立新問題單；執行頻率＝每次問題單建立事件發生時（估計每日約 1–5 次） |
| **涉及的 Sub_Agent_Role** | Explorer（唯讀，製造者，探索問題單關聯的程式碼與既有 Skill_Document）、Implementer（可寫，製造者，撰寫或更新 Skill_Document 內容）、Reviewer（唯讀，檢查者，審查文件正確性與 front matter 完整性）。製造與檢查由不同實例承擔 |
| **使用的 Memory_File** | `TODO.md`（以任務清單語法記錄待分類、進行中、已完成的問題單；進行中事項附負責角色與 Verification 達成狀態） |
| **Verification_Condition** | ①「更新後的 Skill_Document 具備完整 `name` 與 `description` front matter」（可客觀檢查的結構判準）②「Reviewer 依審查準則核准文件正確性」（檢查者核准類） |

**其他涵蓋組件：**

- **Skill_Document**：本 Loop 的主要產物即為 Skill_Document 的新增或更新，須符合第 4 章四欄位標準結構與漸進式披露規則；若專案已有多份 Skill_Document，更新後應同步維護索引清單（見第 4 章 4.3、4.4）。
- **Connector**：需讀取問題追蹤系統中的問題單內容，屬閉環自身無法直接讀寫的外部系統，透過 Connector 接入（見第 5 章 5.1）。

> **參考範例（非規格要求）｜工具：MCP server／client**
>
> 本案例「讀取問題追蹤系統的問題單」在採用 MCP 的落地中，可能以一個對接問題追蹤系統的 MCP server 暴露查詢問題單的工具，Loop 端以 MCP client 連接查詢。server/client 的具體設定屬工具落地細節；規格層僅要求：需要外部存取時使用 Connector、優先考慮 MCP 但不強制、非 MCP 機制須同時記錄能力清單與存取範圍（見第 5 章 5.2、5.3）。

### 12.4 如何改寫這些案例

上述三案例是**起點而非終點**。改寫成自己的 Loop 時，建議依下列方向調整，並以第 9 章設計原則與第 10 章反模式清單逐項檢視：

- **調整觸發與頻率**：依工作是否取決於外部變化，在事件觸發與定時觸發間選擇；新 Loop 建議低頻起步，依產出品質再調整（見第 11.2）。
- **增刪角色**：角色數宜控制在 4 以內以免過度複雜（見第 6、10 章）；務必保持製造者與檢查者為不同實例（見第 6.2、8.4）。
- **強化 Verification_Condition**：把任何主觀措辭改寫為可客觀驗證的判準（見第 8.2），確保每個 Loop 至少一個條件落在測試通過／lint 無錯誤／指標達門檻／檢查者核准之列（見第 8.3）。
- **選用 Memory_File**：依需要選用 `AGENTS.md`／`TODO.md`／`PROGRESS.md` 或其組合，並確保進行中事項記錄負責角色、所屬 Isolated_Workspace（若有）與 Verification 達成狀態（見第 7.3）。
- **評估是否需要 Connector 與 Isolated_Workspace**：僅在需存取外部系統時引入 Connector（見第 5.1）；僅在多角色並行修改同一組檔案時強制各自獨立的 Isolated_Workspace（見第 3.3）。

這些案例對應 Template_Set 中各組件樣板（見第 13 章目錄）：使用者可直接複製相關樣板，依上述方向填寫，快速把參考案例改寫為自己的 Loop。

## 13. Template_Set 目錄

Template_Set 為一組獨立、可直接複製到任何 AI coding agent 專案的無工具綁定 Markdown 樣板，存放於本規格同層的 `templates/` 資料夾。每個樣板對應**一個**組件（第 2–7 章）或**一份**檢查清單（第 9–11 章），共八份。本目錄列出每份樣板的用途、使用時機與建議存放位置（`templates/` 相對路徑），並與其對應章節互相索引：使用者可從章節找到樣板，也可從本目錄回到定義該樣板的章節。

> 索引完整性說明：六大組件中的 **Isolated_Workspace（第 3 章）** 與客觀化驗證標準 **Verification_Condition（第 8 章）** 為概念與規則章節，其落地分別依附於 Isolated_Workspace 機制（如版本控制工作樹）與各 Loop 的 Verification_Condition 定義，**不另立獨立樣板**；其記錄需求已分散落入 `memory-file.template.md`（進行中事項的所屬工作空間與驗證達成狀態）、`sub-agent-role.template.md`（角色存取權限）與 `cost-risk-control.template.md` 等樣板欄位。故本目錄的八份樣板已窮舉所有需要樣板的組件與清單，無孤立章節，亦無未被索引的樣板。
