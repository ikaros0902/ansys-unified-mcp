# Design_Principles_Checklist 樣板

> 用途：設計**新** Loop 時逐項確認的一份正向自我檢查清單，協助設計者在導入自動化的同時，仍保有對產出的驗證責任與理解力，避免把判斷力也一併外包給機器。
> 建議存放位置：專案內 Loop 設計文件旁（例如 `loops/<loop-name>/design-principles-checklist.md`）。
> 填寫說明：設計每個新 Loop 時，逐題自問並勾選。凡無法對某題給出符合原則方向的誠實答案者，代表此 Loop 在該原則上仍有設計缺口，**應先補足再啟用**。將 `<...>` 佔位符替換為實際內容即可，勿寫入任何特定工具的專屬語法或指令。
> 使用時機：新 Loop 啟用前逐項檢視（正向自我檢查）；與反模式檢查清單互補——後者供 Loop 運行一段時間後回頭體檢（負向比對）。

## 原則一：驗證責任歸屬於人（Verification responsibility belongs to humans）

閉環可自動產出、自動依 Verification_Condition 判定完成，但「這個閉環整體是否值得信任、產出是否真的達標」的最終責任，始終歸屬於設計與運行它的人，不因自動化而轉移給機器。

- [ ] 我清楚這個 Loop 的每一項 Verification_Condition 在驗證什麼，並確認這些條件足以讓我**願意為其產出背書**；不存在「我沒真正想清楚、只是先放著讓機器判定」的完成條件。
- [ ] 若這個 Loop 的產出日後出了問題，我能說清楚「當初是依據哪些條件判定它通過的」，而不是把責任推給「是自動化判斷的」。

## 原則二：保持對產出的理解力（Maintain comprehension of output）

設計者應始終能看懂閉環產生了什麼、為什麼這樣產生，並在需要時能親自查核，而不只依賴閉環自身的通過報告。理解力不應隨自動化程度上升而下降。

- [ ] 對於這個 Loop 每一輪的產出，我**仍看得懂它做了什麼、為什麼這樣做**；單輪產出的規模未超過我能實際查核的程度。
- [ ] 這個 Loop 在 Memory_File 或等價處留下了**人可讀**的進度與決策軌跡，讓我在任一會話都能重建對閉環狀態的理解，而不只依賴它自己回報的通過/失敗。
- [ ] `<補充：本 Loop 專屬的其他理解力自我檢查問題（可選）>`

## 原則三：避免認知投降（Avoid cognitive surrender）

設計者應避免因為閉環大多時候運作良好，就停止思考、對其產出與判定一律照單全收。應在設計時就預留保持懷疑的機制，使「持續思考與查核」成為常態，而非可被便利性豁免的選項。

- [ ] 我設計了**定期抽查或人工確認**的機制，讓自己不會因為「它一直都對」就停止查核；這個 Loop 不會在完全無人過問的情況下長期運行。
- [ ] 對於這個 Loop 中**風險較高**的輸出（例如會合併回主線、對外發送、或難以復原的動作），我要求在自動判定之外仍有人保持懷疑並介入確認。
