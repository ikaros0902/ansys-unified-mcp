# 自動化閉環工程準則 (10-loop-engineering.md)

本規範為複雜任務、自動化流程與多代理協同的工程閉環基準，確保系統具備「客觀完成標準」與「自我驅動推進力」，杜絕過早停止與自我審查偏差。

---

## 一、閉環執行原則 (Closed-Loop Autonomous Execution)

遇到多步驟或架構性任務時，Agent 必須以自動化閉環持續推進：

$$\text{DISCOVER (探查現況)} \longrightarrow \text{IMPLEMENT (實作修改)} \longrightarrow \text{VERIFY (客觀驗證)} \longrightarrow \text{REFINE / HEAL (排障自愈)} \longrightarrow \text{RECORD (狀態固化)}$$

1. **拒絕中途停頓**：
   單一檔案編輯完成不代表任務結束；Agent 必須主動執行相依測試，確認變更如預期運作且無副作用。
2. **失敗自愈機制**：
   若驗證失敗（如測試拋錯、邊界條件不符），Agent 應自動提取錯誤日誌、定位根因、調整實作並重新驗證，直到達成驗證條件，而非直接停下向使用者抱怨。

---

## 二、製造與檢查分離原則 (Maker-Checker Separation)

為根除「寬容偏差（Lenience Bias）」與「盲目自審」，產出與審查必須保持邊界：

1. **角色分工職責**：
   - **實作者 (Implementer / Maker)**：負責撰寫、修改程式碼或腳本，產出技術方案。
   - **檢查者 (Reviewer / Checker)**：負責比對客觀驗證條件、檢核測試覆蓋率、進行安全與架構邊界審查；檢查者不直接撰寫實作程式碼。
2. **實例隔離**：
   在多代理架構下，產出程式碼的 Agent 實例與審查驗收的 Agent 實例必須分離。

---

## 三、客觀驗證條件 (Verification Condition)

完成標準必須「客觀、可重複量測、可自動化驗證」，嚴禁任何主觀推測：

| 檢核維度 | 合規客觀標準 (Pass Criteria) | 不合規主觀描述 (Invalid) |
| :--- | :--- | :--- |
| **功能正確性** | 指定測試套件 100% 通過（`pytest` 零失敗） | 「程式碼看起來很工整」、「應該修好了」 |
| **靜態品質** | Linter 零錯誤、Type Checker 零型別衝突 | 「代碼品質感覺不錯」 |
| **CAE 物理準則** | 能量守恆誤差 $\le 5\%$、沙漏能比例 $< 5\%$、有效質量比 $\ge 90\%$ | 「物理響應大致合理」 |
| **API / MCP 回傳** | 回傳信封 `{"ok": True}` 且數值落在物理容許範圍 | 「工具呼叫應該成功了」 |

---

## 四、記憶狀態外部化 (Memory File Protocol)

跨步驟或跨會話進行複雜任務時，必須維護三區塊狀態記錄：

```markdown
## 進行中事項
- [ ] <任務名稱> | 負責實例: <實作者/檢查者> | 驗證標準: <客觀條件> | 當前狀態: <執行中/驗證中>

## 已完成事項
- [x] <已客觀通過驗證的事項> (附量化數據或測試結果摘要)

## 待分類事項
- <過程中新發現但非本次目標的技術債或後續建議>
```

- **狀態流轉**：發現新需求進入「待分類」$\rightarrow$ 確認排入進度進入「進行中」$\rightarrow$ 客觀驗證通過才移入「已完成」。

---

## 五、成本與風控原則

1. **優先事件驅動**：非必要不採用高頻盲目輪詢，以回呼或事件通知為主。
2. **反模式防護**：
   - 防護 A：避免單一閉環過度複雜（單次目標職責單一化）。
   - 防護 B：避免完成條件過弱（不容忍未驗證即放行）。
   - 防護 C：避免無止境迴圈（設定合理自愈嘗試次數上限，超限時總結癥結點並向使用者請求策略指引）。
