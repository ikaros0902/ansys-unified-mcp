# Loop Engineering 框架 - Agent 指導規則

此檔案供 AI Coding Agent（Kiro / Claude / Cursor 等）作為全域指導。在任何任務中，優先按此規則組織工作。

---

## I. 六大組件檢查清單

使用者要求工作時，先問自己這工作是否涉及「自動化閉環」：

### ✓ 涉及自動重複執行
- [ ] 定義觸發條件（Automation_Trigger）：何時啟動？定時還是事件觸發？
- [ ] 設計代理角色分工（Sub_Agent_Role）：製造者 vs 檢查者是否分離？
- [ ] 明確完成條件（Verification_Condition）：如何判定完成？（不可主觀）
- [ ] 建立記憶文件（Memory_File）：跨會話狀態如何保留？
- [ ] 規劃工作隔離（Isolated_Workspace）：多角色並行時如何無覆蓋？
- [ ] 列出所需技能（Skill_Document）：代理需知道哪些專案知識？

### ✗ 一次性工作（非自動化閉環）
- 正常流程處理，無需此檢查清單

---

## II. 三大設計原則

設計或審查任何自動化 Loop 時，問自己：

### 原則 1：驗證責任歸屬於人
**問自己**：「我是否清楚此 Loop 的每一項完成條件在驗證什麼，並願意為其產出背書？」

**具體做法**：
- 不信任「自動判定就是對的」
- 定期抽查 Loop 產出，驗證完成條件確實有效
- 若不願背書，停止該 Loop 並修正條件

### 原則 2：保持對產出的理解力
**問自己**：「我是否看得懂每一輪的產出做了什麼、為什麼這樣做？」

**具體做法**：
- 控制單輪產出規模（不超過自己能實際查核的程度）
- 要求 Loop 在 Memory_File 留下可讀的進度軌跡
- 若產出規模超出理解力，拆分為更小的子 Loop

### 原則 3：避免認知投降
**問自己**：「我是否因為『它一直都對』就停止思考？」

**具體做法**：
- 設計定期抽查或人工確認機制
- 高風險輸出（合併回主線、對外發送）要求人工複核
- 不讓任何 Loop 在完全無人過問下長期運行

## III. Verification_Condition 撰寫規則

完成條件**必須客觀、可重複驗證**，不接受主觀描述。

### ✓ 合規寫法（自動判定 / 人工審查都能驗證）
- 「指定測試套件全部通過」
- 「靜態檢查 (lint) 零錯誤、零警告」
- 「覆蓋率 ≥ 80%」
- 「p95 延遲 ≤ 200ms」
- 「Reviewer 依審查準則核准」（Reviewer 必須是不同角色實例）

### ✗ 不合規寫法（主觀、結果因人而異）
- 「程式碼品質看起來不錯」
- 「測試應該都有過」
- 「效能大致可接受」
- 「這個 bug 感覺修好了」

**改寫原則**：把「感覺 / 看起來 / 應該」，改為「哪個工具、達到哪個可量測或可核准的判準」。

---

## IV. 製造 / 檢查分離規則

自動化 Loop 中的**製造者與檢查者必須是不同的角色實例**。

### ✓ 正確分工
```yaml
assign:
  - role: implementer      # 實作者
    work: code
  - role: reviewer         # 檢查者（不同實例）
    work: verify
```

### ✗ 錯誤分工
```yaml
assign:
  - role: implementer
    work: "code and verify"  # ❌ 自我審查，寬容偏差
```

**為什麼重要**：製造者傾向認可自己的成果，使審查形同虛設。分離打破此偏差，維持審查可信度。

## V. Memory_File 更新規則

每輪 Loop 執行完畢，**必須**更新 Memory_File 狀態。

### 三區塊結構
```markdown
## 進行中事項
- [ ] <事項> | 負責角色: <角色> | Workspace: <隔離空間> | Verification: <達成狀態>

## 已完成事項
- [x] <已驗證完成的事項>

## 待分類事項
- <新發現但未指派的工作>
```

### 更新時機
- 發現新工作 → 進入「待分類事項」
- 指派給角色 → 移入「進行中事項」，記錄負責角色、工作空間、驗證狀態
- 通過驗證 → 移入「已完成事項」
- **每輪執行後皆須更新**（不是累積數輪才寫）

## VI. 成本與風控規則

### 執行頻率建議
- **低頻起步**：新 Loop 先以低頻運行，觀察產出品質
- **依品質調整**：品質穩定後逐步提高頻率；品質不穩則降頻並修正
- **優先事件觸發**：若 Loop 的工作「有變化才反應」，用事件觸發避免空轉成本

### 模型分層
| 任務類型 | 推薦模型量級 | 例子 |
|---------|-----------|------|
| 機械性例行工作 | 輕量 | 格式整理、依清單勾稽、資訊擷取 |
| 一般開發工作 | 主力 | 撰寫代碼、寫測試、彙整發現 |
| 高難度推理 | 強推理 | 複雜架構決策、根因分析、嚴謹審查 |

### 成本上限
每個 Loop 須設定 `budget`（成本或執行次數上限）並定義超限時的處置（暫停、降頻、告警）。

## VII. 反模式防護

認出以下症狀時立即修正：

### 反模式 A：Loop 過度複雜
**症狀**：
- Sub_Agent_Role 數量超過 4 個
- 無法用一兩句話說清 Loop 目標
- 進行中事項長期堆積

**修正**：拆分為多個各自單一職責的子 Loop

### 反模式 B：Verification_Condition 過弱
**症狀**：
- Loop 幾乎從不因驗證失敗而停下
- 「綠燈」頻繁出現但實際產出品質參差
- 製造者自己檢查自己（製造/檢查未分離）

**修正**：改為客觀、嚴格的完成條件；確實分離製造與檢查

### 反模式 C：忽視成本管理
**症狀**：
- 無成本上限或無超限處置
- 高頻定時觸發在無變化時仍反覆空轉
- 成本持續上升卻無人監看

**修正**：設定 budget、優先事件觸發、定期監控

## VIII. 實務檢查清單

### 設計新 Loop 時
- [ ] 六大組件皆已定義（觸發、隔離、技能、連接、角色、記憶）
- [ ] Verification_Condition 為客觀、可重複驗證的標準
- [ ] 製造與檢查指派給不同角色實例
- [ ] Memory_File 結構完整（進行中 / 已完成 / 待分類）
- [ ] 成本上限與超限處置已明確記錄
- [ ] 可用一兩句話說清 Loop 目標

### 運行一段時間後（定期體檢）
- [ ] 隨機抽查 3–5 個「通過」的產出，驗證完成條件確實有效
- [ ] Memory_File 進度軌跡清晰、便於重建理解
- [ ] 未發現製造/檢查混淆情況
- [ ] 成本消耗在預期範圍內
- [ ] 沒有無人看守長期運行的狀況

## IX. 根據框架調整 Prompt

向代理下達工作時，若涉及自動化 Loop，加入此指導：

```
根據 Loop Engineering 框架完成此工作：
1. 明確觸發條件（何時啟動）
2. 設計角色分工（製造 vs 檢查分離）
3. 定義客觀完成條件（不可主觀）
4. 規劃記憶檔案（狀態保留）
5. 評估成本與風險（頻率、模型選擇、上限）
6. 通過設計原則檢查清單（三大原則）

使用樣板：templates/design-principles-checklist.template.md
參考文件：loop-engineering-specification.md
```
