## 2026-10-14：Skill 結構補齊與閉環驗收

### 1. `skill-creator` 的 `assets/` 定義範圍很窄，勿無差別套用

官方 `skill-creator`（`D:\Ikaros\skill-creator\SKILL.md`）定義 `assets/` 僅限「會被輸出產物直接引用的靜態素材（模板、圖示、字型）」，不是每個 skill 的標配第四層目錄。遇到「補齊標準結構」類需求時，先查官方規範的實際定義範圍，再逐一判斷每個 skill 是否真有「固定輸出格式」的需求，不要見到三層結構就機械套用成四層。

**判斷標準（三條同時成立才該放）**：
1. 該 skill 確有「生成具體產出物」的職責。
2. 產出物有重複出現的固定格式骨架（非每次臨時手刻字串）。
3. 抽出模板比寫在程式碼內的字串拼接更好維護。

若經盤點後確實要全面補齊（如使用者明確要求），無模板需求的 skill 應放置「說明性占位文件」並客製化說明其職責為何目前不需要模板，而非空目錄或泛用罐頭文字。

### 2. Windows PowerShell 複合指令在 shell 工具中不穩定

透過 `shell` 工具執行以 `&&`、`;`、`|` 串接的複合 PowerShell 指令時，容易回報 `exit code 1` 但無任何 stdout/stderr 輸出，無法判斷實際失敗原因。拆成單一指令依序執行可穩定取得結果。遇到這種「exit 1 但無輸出」的情況，優先懷疑是複合指令語法問題，而非邏輯錯誤，直接拆開重試比排查更省時間。

### 3. 驗證「改動是否引入回歸」優先用 `git stash` 排除法

流程：
1. 跑一次完整測試套件，記錄失敗清單（含測試名稱）。
2. `git stash` 暫存本次改動。
3. 再跑一次同樣的失敗測試。
4. 若失敗集合不變 → 客觀證明失敗與本次改動無關，屬既存問題。
5. `git stash pop` 還原改動。

這比憑印象或程式碼邏輯推測「這應該是既存問題」更具客觀證據力，符合 Claims-Evidence 門禁要求。

### 4. 官方/第三方驗證工具的檢查範圍可能落後於專案既定慣例

`skill-creator/scripts/quick_validate.py` 僅允許 `name`/`description`/`license`/`allowed-tools`/`metadata`/`compatibility` 六個 frontmatter 欄位，但專案內多數 `SKILL.md`（含本次新建的）普遍使用 `Use when:` 擴充欄位來條列觸發情境與限制。遇到驗證工具報錯時，先確認是「本次產出真的有缺陷」還是「驗證工具的檢查規則落後於專案實際慣例」，不要盲目把驗證失敗等同於產出錯誤。

### 5. 製造與檢查分離在跨目錄規模化任務中的具體效益

本次 24 個 skill 的 `assets/` 補齊透過 `implementer`（兩軌平行：模板型 + 占位型）與獨立 `loop_reviewer`（opus-5, effort=xhigh）分離執行，reviewer 確實抓到 implementer 自述「全文純 ASCII」但實際第 3 行含中文的矛盾（ACT manifest 範本違反全英文規範）。若由同一實例產出與驗收，這類「自己講的話與自己做的事不一致」的落差容易被自我確認偏差掩蓋過去。
